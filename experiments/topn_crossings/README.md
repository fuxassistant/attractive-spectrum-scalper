# Top-N первых пересечений: недельный прототип

Исследовательская ветка: `codex/research-topn-crossing-labels`, база
`baseline-0.3.0`. Runtime библиотеки не меняется. Код зависит от библиотеки;
обратной зависимости нет. Обучение модели в этом опыте не выполняется.

## Вопрос и определение метки

Для известных будущих данных найти top 1, 2, …, n сделок, покрывающих большую
сумму положительных исходов при явно заданной уникальности. Кандидат:
`(origin, scale, role, side)`. Выход — **строго первое** пересечение выбранной
линии после origin, в том же support. Используется полный исходный банк,
включая дребезг. Более раннее пересечение нельзя пропустить ради лучшего.

Origins — все сохранённые публикации reduced quote tape с допустимым BBO
и открытым каноническим календарём. Это не полная сырая последовательность
MBO и не непрерывное множество всех наносекунд. Данные первой недели:
торговые сессии 4–8 мая 2026, включая их начало предыдущим вечером UTC.

Деньги считает `spectrum.economics.future_crossing_marks`: LONG покупает ask
входа и продаёт bid выхода; SHORT наоборот. Единица USD на одну условную унцию;
комиссия полного оборота 0.30 USD/oz из канона. Нет latency, fill, impact,
стопов, плеча, размера капитала или доказательства исполнимости.

Два определения top сохранены отдельно:

1. **Event-top.** Все входы и обе стороны, ведущие к одному `event_id`,
   конкурируют за одно место. Для фиксированного выхода лучший LONG достигается
   на минимальном entry ask, лучший SHORT — на максимальном entry bid.
   Выигравшие положительные исходы сортируются по net. Получается вложенный
   top-n; n не является числом обязательных сделок стратегии.
2. **Exact origin/event matching.** Максимальная сумма для до k сделок,
   причём ни `event_id`, ни timestamp открытия не повторяется. Применён
   точный min-cost flow, k=1..32. Решения при k и k+1 могут перестраиваться;
   они сохранены как отдельные assignments, а не ложный стабильный rank.
   Это выполняет буквальное «одно открытие — один исход», но по-прежнему
   разрешает перекрытие интервалов и противоположные позиции.

Сортировка использует net с точностью 1e-8 USD/oz, затем ранний origin,
ранний exit, scale/role, сторону и event ID. В exact matching стоимости
целочисленные с той же точностью. На outcome достаточно K лучших различных
origins: в решении размера <=K занято максимум K−1 других origins, поэтому
усечённое ребро всегда можно заменить сохранённым без потери результата.

В каждом окне также считаются контрольные варианты: объединение по quote
ordinal физического выхода, по `cluster_event_id`, greedy unique-entry и
greedy non-overlap. Два последних используют только независимых лучших
представителей. **Их потери не являются ценой оптимального ограничения**:
они выбрасывают альтернативные входы. Non-overlap здесь — допустимое жадное
подмножество, не максимальная доходность исполнимой стратегии.

## Окна и время зрелости

| Режим | Входы и допустимые выходы |
|---|---|
| `time_30m`, `time_60m` | Оба конца сделки внутри одного полуоткрытого окна `[start,end)` |
| `time_30m_shift15` | Та же постановка со сдвигом сетки на 15 минут |
| `events_512`, `events_2048` | Границы по K различным публикациям с raw crossings; группы одного timestamp не разрываются |
| `opportunities_128` | Границы по 128 публикациям новых opportunities; сами выходы всё равно из полного raw bank |
| `time_30m_h60`, `time_60m_h60` | Origins внутри окна 30/60 минут; для каждого origin одинаковый горизонт выхода 60 минут вперёд |

Для contained окон rank созревает в конце окна. Для H60 — в
`min(window_end + 60min, session_coverage_end)`; отсутствие будущего после
границы support/session — отдельная цензура. Последнее неполное окно явно
помечено. NOT_READY, ограничение окна/горизонта и SUPPORT_END не превращаются
в убыток или нулевой исход. Отчёт отдельно показывает их доли.

H60 устраняет искусственное сокращение горизонта для позднего входа в окне.
При этом один outcome может встречаться в нескольких соседних origin-окнах:
уникальность локальна для набора. Их суммы не складываются в недельный капитал.

## Файлы и воспроизведение

Численные расчёты выполнялись в закреплённой baseline-среде. Plotting отдельно
использовал доступный локальный matplotlib 3.11.1; он не добавлен в зависимости
библиотеки и не участвует в выборе меток.

```powershell
$py = '.tmp/baseline/venv/Scripts/python.exe'
& $py -m pytest -q experiments/topn_crossings checks
& $py experiments/topn_crossings/run.py --output research_results/topn_crossings/NEW_RUN
& $py experiments/topn_crossings/matching.py research_results/topn_crossings/NEW_RUN
# Рендер требует matplotlib; укажите отдельный plotting-интерпретатор.
.venv/Scripts/python.exe experiments/topn_crossings/plot.py research_results/topn_crossings/NEW_RUN
```

Каждый основной run требует нового каталога. Исходные данные read-only и
сверяются с паспортом baseline. `manifest.json` содержит конфигурацию,
версии, SHA-256 кода, входов и результатов. `code_commit` — HEAD, от которого
начат запуск; незакоммиченный код определяется отдельными source hashes.

Недельный результат этой работы:
`research_results/topn_crossings/week_20260504_v2/`.

- `labels/<day>/<mode>.parquet`: все лучшие представители исходов, включая
  неположительные с rank=0; отдельно лучшие LONG/SHORT, времена, net, число
  конкурировавших origins, событие/кластер, maturity.
- `top.parquet`: первые 32 положительных представителя каждого окна.
- `windows.parquet`, `curves.parquet`, `summary.json`: покрытие, цензура,
  распределения n50/n80 и сравнение определений уникальности.
- `matching/`: точные кривые k=1..32 и assignments при k=1,3,10,32.
- `figures/`: PNG и SVG; `SOL_REVIEW.md`: независимый визуальный разбор Sol 6.1.
- `source_snapshot/`: сохранённый код фактической генерации для проверки её
  хешей. Последующие исправления пустых агрегатов и selector не изменяют метки.
- `analysis.json`: проверка хешей, 5 048 031 first-crossing ссылок и диагностика
  повторного использования событий/движений.

Все сериализованные поля имеют префикс `future_`. Используйте `read_labels`,
который возвращает FutureFrame, и `select_top_n(labels,n)` для event-top.
Selector добавляет вес `net_i / sum(net_top_n)`; это относительный вклад
в oracle-сумму, **не вероятность и не уверенность модели**. Максимальный rank
полной partition не ограничен 32; ограничены обзорные графики и matching.

На текущем run `analyze.py <run>` проверяет сохранённый source snapshot,
хеши и соответствие всех выбранных входов их первым raw crossings.

## Что пригодно для дальнейшего обучения

Рабочий следующий контракт — **окно origins 30 минут, fixed H60**, 60/H60
как проверка чувствительности. Это выбор постановки по структуре меток,
не выбор лучшей модели по торговому результату. Полная неделя — development
sample; она не является независимым test-set после такого исследования.

Метки описывают будущие альтернативы одного движения. Отдельно понадобятся
примеры для всех причинных origins, включая проигравшие/цензурированные,
regret относительно выбранного outcome, устойчивость к задержке входа и
издержкам, состояние позиции и допустимое действие WAIT. Одних выбранных
постфактум экстремумов недостаточно для обучения входам.

X должен иметь `available_ns <= decision_origin`; окно, rank, n80, выбранный
event ID и лучшие entry timestamps являются Y. Хронологические splits
должны учитывать maturity и повторённые event IDs. Размер будущего лучшего
набора нельзя подмешивать в X как заранее известный признак. После обучения
оценка должна идти на новой неделе последовательным исполнением с издержками.

Смысл и числа первой недели записаны в локальном `REPORT.md`; тяжёлые данные
и исследовательские отчёты остаются вне Git. Бейслайн и его тег сохранены.
